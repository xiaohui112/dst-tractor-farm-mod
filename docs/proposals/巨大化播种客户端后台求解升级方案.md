# 巨大化播种客户端后台求解升级方案

**状态：备选方案，暂不实施。** 整理于 2026-11-23，基线为 Mod 0.5.28（`9fe4bc9`）。本文用于后续性能升级评审。现行玩法、参数和验证状态见[播种机说明](../equipment/03-播种机.md)和[版本验证报告](../03-版本测试报告与Bug修复.md)。

## 1. 升级目标

缩短驾驶员按 F 后等待巨大化播种预览的时间，尤其是预计算未命中、必须现场规划的场景。由驾驶员电脑上的独立工作线程或辅助进程连续运行同源 Lua 求解器。服务器负责采集农田和库存、核验方案、提交预览和实际落种。

第一阶段建议只在「巨大化·最优」验证这条链路，优先覆盖**合法布局达到服务器可独立复算的数量上界**的场景。随后根据命中率和实测收益，再决定是否扩展未达上界的精确证明和「巨大化·模版」。顺序模式照常运行。最优模式仍以本轮完整有效连通农田为范围，以最大合法播种数量为第一目标，再按现有规则整理图案。

## 2. 现状与提速来源

现行流程从播种机落种口所在的地皮开始，服务器扫描可用农田及车仓种子，使用世界内串行的 Lua 协程求解，再生成绿色预览。前台共享每帧软额度默认 16 ms，后台预计算固定 1 ms。最优可利用空闲预计算、暂停续算和完整方案缓存。预览显示后现行自动开种等待为 2 秒，播种机在目标地皮内才会落种。[调度实现](../../mod/Tractor/scripts/aom_dynamic_farm.lua) · [预算实现](../../mod/Tractor/scripts/aom_plan_budget.lua)

| 运行位置 | 对分帧的影响 | 适用方向 |
|---|---|---|
| 服务器游戏 Lua 主线程 | 仍需按服务器帧让出执行权 | 保留为权威求解和回退路径 |
| 驾驶员客户端游戏 Lua 主线程 | 连远程专用服时，服务器在独立进程中运行。客户端主线程长时间执行 Lua 仍会拖住本机画面、输入和游戏更新 | 可用于收发消息和显示状态 |
| 驾驶员本机的工作线程或辅助进程 | 求解可连续运行，忙时可接近占用一个逻辑核心的计算份额。由操作系统调度，同机开服时仍共享 CPU、内存与散热 | 用于搜索和排列整理 |

Lua 协程仍可用于在求解器内部轮转精确搜索和辅助构造、上报进度或响应取消。独立工作进程允许这些协程立即继续运行，省掉与游戏帧绑定的等待。服务器扫描、消息解码、几何验收和结果提交仍须控制主线程单帧开销。单线程计算本身仍受 CPU 单线程性能、运行时和输入复杂度影响。[Lua 5.1 协程参考](https://www.lua.org/manual/5.1/manual.html#2.11)

## 3. 运行方式与可行性检查

| 方式 | 用途 | 开工前核对项 |
|---|---|---|
| 网页验证器的 Dedicated Web Worker | 首选离线原型。现有页面使用 Lua 5.1.5 WebAssembly 在浏览器后台运行同源算法，可复用源码打包、进度、结果提取和取消机制 | 增加真实农田快照输入，核对真实邻接、运行时和结果一致性。现有网页入口使用模拟地图和规则快照，尚无游戏联动 |
| 玩家明确启用的本机辅助进程 | 首选实机原型候选。由它持有独立 Lua state，游戏通过发行渠道允许的接口交换数据 | 在现行 DST 客户端和目标平台确认受支持的双向通信、启动/退出行为及分发方式。离线可跑与能在 Steam 创意工坊环境无感接入属于两项验收 |
| 游戏正式支持的原生后台线程接口 | 若后续存在受支持的接口，可省去单独安装辅助进程 | 核对接口可用性、跨平台支持，以及线程能否持有独立 Lua state。源码基线尚无这一接入路径 |

优先复用 Mod Lua 模块和版本指纹工具。第一轮对照保留原算法、规则和候选预算，只改变运行位置及调度。纯 Mod 可发布性取决于游戏和发行渠道支持的接入方式。若找不到受支持的通道，保留服务器分帧路径，原型继续用于离线性能验证。[网页运行时说明](../../web/giant-seed-verifier/browser/README.md) · [源码指纹工具](../../tools/planner_fingerprint.py)

## 4. 游戏内流程和数据约定

1. **触发。** 驾驶员按 F 后，服务器按现有规则检查骑乘、播种机、模式和作业地皮。优先续播已有正式计划，或复用符合当前输入的完整缓存。只有需要新求解且本机能力已就绪时，才把任务交给驾驶员的工作进程。
2. **取快照。** 服务器采集从落种口起点扫描到的完整有效农田、各坑的实际位置和车仓种子；统一地皮与坑位编号，记录模式、季节、规则指纹和现场代次。扫描分多帧时，提交快照前核对采集期间的变化，避免把两个时点的现场拼成一个输入。
3. **连续求解。** 驾驶员本机在独立 Lua state 中处理快照，沿用数量证明、图案整理和相应工作量预算。游戏主线程负责接收紧凑进度和转发结果。后台计算期间不进入正式预览，也不消耗种子、燃料或耐久。
4. **核验。** 服务器比对会话、任务代次、申请者和当前现场。将返回的坑位编号映射回服务器记录的坐标，重算用量和实际株数，再验证空间、配比和数量证明。输入变化时按第 6 节处理。
5. **落种。** 通过核验后，由服务器走现有正式计划、绿色预览、2 秒等待和播种入口。预览与下种由服务器同步，仍以落种口位置和成功落种为准，沿用逐格耗油、底盘和挂件耐久结算。既有存档计划继续走原流程。

### 请求与结果

以下字段用于明确职责，具体消息名和编码等通信原型确认后确定。

| 数据 | 建议内容 |
|---|---|
| 能力协商 | 协议版本、算法源码指纹、有效原版规则和目录指纹、可支持策略。房主/服务器决定是否启用，驾驶员的工作进程可用时才接单 |
| 求解请求 | 世界会话、任务编号和代次、发起车与驾驶员绑定、快照摘要、模式、季节、有效作物与作物种子数量、地皮和真实坑位、各半径下的邻接及冲突关系、求解所需常量、锁定模版 ID（扩展时使用） |
| 进度 | 任务编号、实际阶段、已运行时间。数量阶段可报告已找到的合法下界，只有可复核时才显示上界。无需高频发包或预测剩余时间 |
| 求解结果 | 任务编号、快照摘要、坑位编号与作物编号的对应关系、证明方式及校验所需的数据。用量和计时可附作诊断。模版扩展时补充模块编号、起点、方向及角色对应 |

**原版几何以服务端为准。** 当前使用 `FindEntities` 按实际坑位与原版范围规则建立同族邻接及坑距冲突。建议由服务器采集相应的稀疏关系并发给工作进程，保留原始查询结果；跨平台时在同一份输入上对照布局和数量证明。坐标用于排列和恢复现场落点，硬约束使用服务器采样的关系，覆盖旧坑、边界坐标和跨地皮同族。[原版查询适配](../../mod/Tractor/scripts/aom_farm_neighbors.lua) · [求解几何](../../mod/Tractor/scripts/aom_seed_layout.lua)

**控制传输成本。** 只向当前驾驶员定向发送作业必需数据。对任务数、消息字节数、分片数、重组空间与超时设上限，由实机测量定值。最优沿用最多 64 块地皮；将来支持模版时，载荷超过客户端能力上限则回到服务器现有流程，模版的玩法范围不受此传输上限影响。请求和结果应使用单独通道，继续用现有预览协议显示附近地皮。

## 5. 服务器如何确认最优

每个结果先检查任务身份和结构，再按服务器快照和当前世界复核。只接受合法坑位编号和当季作物，每坑一次，累计用量不得超过当前车仓库存。复用现有坑距、密度、逐株同族、逐地皮养分净零和模版规则校验。提交正式计划前检查快照仍有效，实际落种时继续做现有现场复核。客户端的 `optimal`、`total`、`upper` 和运行时指纹均不能单独作为数量证明。

| 客户端结果 | 服务器处理 |
|---|---|
| 合法布局的株数达到服务器独立计算的安全上界 | 可以确认最大数量。先评估现有 `Balance.Upper` 等可独立复算的放宽上界，降低服务器为验收再次运行完整搜索的概率。上界计算也要测主线程成本，并按预算推进 |
| 合法布局低于服务器可复算的上界 | 作为当前可行下界或后备搜索的起点。服务器分帧排除所有更大的合法布局后才能确认完成。接收并复用外部下界、保留已有搜索进度需要后续实现和回归 |
| 报告已完成精确搜索、无解、超时或只返回中间结果 | 只有服务器能以同一快照独立证明或核验完整证明时，才确认最优或无解。超时、取消、启发式试探失败或未能核验的证明回到服务器路径 |
| 模版选配结果（后续扩展） | 按审核目录核验版本、完整模块、允许的角色和方向、必要留空、合法补块与全田硬约束。模版保持现有选配含义，无最大数量证明要求。以同源结果和图案质量作回归，防止选配缩水 |

第一阶段采用前两行的可复算上界与服务器后备路径，先测多少请求可以免去服务器精确搜索。若复杂长尾覆盖率不足，再评估可重放的证明数据是否比服务器重算更便宜，或继续优化求解器。排列整理沿用固定数量后的现有预算和评分，验收时同时检查布局合法性、最大数量及图案质量。[数量上界实现](../../mod/Tractor/scripts/aom_seed_balance.lua) · [数量证明与排列实现](../../mod/Tractor/scripts/aom_seed_packing.lua) · [最优设计与验证报告](../reports/巨大化最优设计与验证报告.md)

## 6. 失效、取消和回退

| 事件 | 处理 |
|---|---|
| 同一片田内移动车辆，或车仓仅更换槽位 | 若实际有效输入相同，继续同一任务。开种仍以落种口位置为准 |
| 种子数量或季节变化，坑位/障碍/连通范围变化，模式或有效规则变化 | 作废旧代次。若仍在作业并符合新输入，按新快照重算；合并连续装料或改地的变化。正式开种后的停工、续播沿用现行规则 |
| 再按 F、换挡至其他播种模式、下车、拆挂件、换驾驶员、退服或切换世界 | 作废任务并通知工作进程取消。忽略过期结果，回收待重组包和临时数据。若重新发起任务，可复用相同快照已核验的结果 |
| 工作进程未安装、未启用、版本不符、崩溃、通信超时或验收不通过 | 自动使用服务器分帧路径，保持原播种操作。超时只用于切换执行位置，数量证明仍按原规则继续 |
| 多车、重复包或乱序结果 | 按世界会话、拖拉机、驾驶员和任务代次配对；同一任务只提交一次。建议原型对每个本机工作进程限制一个前台任务，服务器重验与回退继续共享世界预算 |

第一阶段保留服务器已有预计算。正式请求优先复用有效缓存和在途服务器任务；当前台任务确实交给客户端时，避免默认同时跑两份完整求解。客户端失联后，优先复用仍有效的服务器进度，再选择重启。对慢客户端与快专服的组合，应比较回退和等待上限所产生的长尾。客户端进度提示可沿用现有头顶和控制台反馈。

## 7. 性能基准与验收

### 计时口径

对同一批输入分别测「服务器分帧」「同机同源连续执行」「完整客户端联动」。固定源码、规则、目录、起点、实际坑位和种子数量，缓存命中与冷启动分开测。以单调时钟测墙钟，各自记录扫描和取快照、传输及排队、客户端初始化、数量、排列、服务器核验或回退、预览出现和首次实际落种。跨机器分别记录阶段耗时，由同一端记录端到端时间，避免直接相减两台机器的时钟。可用时另记工作线程 CPU 时间，浏览器 Worker 的现有计时按浏览器经过时间记录。

**主指标为按 F 到预览的墙钟时间**，同时报告按 F 到首种的墙钟时间、服务器与客户端主线程长帧、不同阶段 P50/P95/最长值、客户端完成率、上界直验通过率、回退率、消息大小和峰值内存。首种数据需记录是否驶离目标地皮，以免把行驶时间或固定 2 秒误算成规划时间。历史性能报告只用于挑选场景，上线门槛在取得实机基线后再定。[历史性能对照](../03-版本测试报告与Bug修复.md)

### 最低验证矩阵

| 项目 | 必测场景与通过条件 |
|---|---|
| 正确性 | 小田、秋季满库存九格、5×5、7×7、64 格边界、旧坑、变形边界、非默认原版规则及无解输入。最优数量与现有完整求解一致；布局通过独立约束校验；排列质量按既有评分回归。优先包含能达到安全上界与必须完整证明两类输入 |
| 状态与多人 | 规划中增减种子、换季、改坑、换司机、下车、停工、断线重连、重复回包、两个车手争用同一片田、服务器重进世界。验证旧任务无提交、有效任务只提交一次、实际落种不重复计费、旧存档仍能续播 |
| 兼容与回退 | 外部工具未安装、版本不匹配、进程异常、结果格式错误、分片缺失或过量、证明不通过，以及模版大田超出传输能力。验证游戏保持可操作并自动回到原有路径 |
| 实机性能 | 远程专服、房主同机自玩、多人多车、快服慢客户端与慢服快客户端各测一组。若能取得用户的 Intel Core i7‑7700 实机，把它设为现有客户端基线，再选一台较新机器对照。复杂场景的等待和服务器长帧应有可复现改善，简单场景避免被初始化和传输拖慢 |

## 8. 后续实施顺序

| 阶段 | 交付 | 进入下一阶段的条件 |
|---|---|---|
| A. 离线基线与快照回放 | 为真实农田记录可回放快照，复用 Lua/WASM 验证器跑同源连续求解，对照服务器原生邻接、布局和数量 | 验证同一输入的硬约束、数量和排列质量；指出瓶颈在搜索、分帧、扫描还是验收 |
| B. 在真实客户端证明通路 | 在受支持的接入方式上验证会话绑定、定向传输、取消和迟到结果处理；可先只比较结果，正式播种仍由现行路径控制 | 目标环境下可稳定复现进度与结果交换，主线程无明显额外长帧，失败时能回退 |
| C. 小范围启用最优快速路径 | 有效客户端返回达到服务器可复算上界的合法布局，服务器走既有预览和落种；其余继续服务器证明 | 完成离线回归与实机多人验证，确认数量一致、收益覆盖传输/核验，并保留房主可关闭的回退入口 |
| D. 评估长尾和模版扩展 | 依据上界命中率、实际 P95 与失败样本，选择改善搜索、可验证证明或扩展模版与后台准备 | 扩展项各自证明收益及兼容性，再决定是否纳入下一版本 |

现有[等待优化提案](巨大化播种等待优化备选方案.md)记录预计算、缓存和续算的历史路径。本方案复用这些能力，重点评估必须现算时，把计算移出游戏主线程能节省多少等待。
