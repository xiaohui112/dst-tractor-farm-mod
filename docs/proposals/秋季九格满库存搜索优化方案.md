# 秋季九格满库存搜索优化方案

2026-11-16。状态：原因分析与方案，未修改 Mod。以下局部搜索使用离线 CP-SAT 验证可行性，不代表已经实现或测量了对应的 Lua 优化。

**后续诊断修正：先处理数值边界与引擎一致性，再评估以下搜索优化。** 只在离线几何层处理半径边界浮点误差、保持搜索算法不变，该场景约0.174秒墙钟就达到并证明81株。原先把局部修补排在第一优先级过早；“原版严格比较”也需区分规划器Lua计算与原版引擎的FindEntities。详见[浮点原因分析](../evidence/family-distance-2026-11-16/原因分析.md)。下文保留为原始诊断记录和后备优化方案。

## 结论

优先增加一个通用的、有工作量预算的“围绕已有合法解修补缺口”步骤，放在初始构造之后、区域探测和全局配额准备之前。保留原有完整搜索作为后备。

该场景并非上界不清楚：容量就是 81，Lua 很快找到 80。关键是没有优先利用已有 80 株布局，只为最后 1 株调整少量坑位，而是在多种区域构造、全田配额和全田重排之间消耗时间。

实测固定其余 8 块地皮，只开放缺口所在的 1 块地皮，调整 3 个坑即可达到 81。完整独立校验和 Lua 校验均通过。这比立即重写整数规划、通用 SAT 求解器或增加秋季专用模版更值得先验证。

## 为什么会超时

### 1. 已经离最优很近，但初始构造的模块边界限制了最后一步

初始方案由四组 18 株模块加最后一格 8 株组成，共 80。最后一格是土豆4＋番茄4，中心留空。模块自身合法，但初始构造没有逐坑修改该格配比、利用相邻模块提供的同族支持来补成 9 株。

本次带诊断的 20 秒 CPU 复现：

| 阶段 | CPU 秒 | 观察 |
|---|---:|---|
| 配比、几何、上界 | 0.014 | 457 个合法单格配比，数量上界81 |
| 初始构造 | 0.067 | 已有合法80株 |
| 区域探测 | 0.680 | 反复尝试独立区域，没有达到81 |
| 同配比重复铺田 | 0.307 | 没有找到合法81株 |
| 全局配额准备 | 0.718 | 枚举达到100万节点预算，仅得到部分配额 |
| 多路全局搜索 | 18.269 | 截止仍是80/81 |

这些是一次插桩诊断的 CPU 耗时，用于定位，不与上一轮墙钟成绩直接比较。

### 2. 独立区域构造会反复碰到边界同族障碍

本次记录到 56 次“三格区域目标27、最终最多24”的精确子调用。区域构造把这些局部区域独立求解，不把相邻区域的作物当作支持条件，因此可能错过全田合法的跨区域配合；它只提供候选，未把局部失败错误用于全局无解证明。

简单整田重复“胡萝卜3＋玉米3＋土豆3”横条纹，81坑全部种满，但有一个角落的土豆只计到3株同族。两个临界支持点的平方距离为 `16.000000000000007`，超过原版严格阈值 `16`。同一角坑没有半径内的外地皮支持点，因此其同族支持必须来自本格；每类仅3株的配比不能让该坑合法。

这解释了为什么理想纸面排列看似可行而实际检查失败。方案继续使用现场原始坐标和严格比较，不加 epsilon、不移动坑位、不修改同族判定。仅交换最后一格两株不同作物的 27 种尝试也全部失败，说明不能把它简单视为交换一次就能解决的排列问题。

### 3. 配额准备较早成为必经步骤，部分配额又引导了后续搜索

`Exact.Prepare → Balance.TargetAllocations` 在目标81上到达 1,000,001 个节点，返回 `limited=true` 和 174 个配额。

独立准备测试中，CP-SAT 原始81株解对应的规范化配额不在这174个配额里。这个观察不证明174个配额都不可行，但说明先搜这批配额不一定接近已经知道存在的解。

代码保留了不固定配额的短探测以及最终完整后备，因此并未丢掉正确性。问题在优先级：174个配额生成三类分支顺序，加上不限配额后备，共523个任务。诊断结束时主搜索还在第4个配额，辅助路径已经退化成第二条全局精确搜索，走到第91个配额，两条都还没有达到81。

### 4. 按协程恢复次数分配份额，不能保证 CPU 份额

`quantity_portfolio` 给主精确搜索每轮1次恢复，辅助构造8次；辅助构造失败后也会进入 `Exact.Maximize`。

本次全局搜索阶段中，主路径消耗约1.335 CPU秒，辅助路径约16.882 CPU秒。主路径只得到约7.3%的这两条路径时间。它们都大量搜索相同配额空间，仅分支顺序和状态不同；这不是 CP-SAT 的多核并行，实际仍在单个 Lua 执行线程中轮转。

来源：[阶段与搜索状态摘要](../evidence/cpsat-autumn-analysis-2026-11-16/profile-summary.json)、[完整诊断数据](../evidence/cpsat-autumn-analysis-2026-11-16/profile-detailed.json.gz)。

## 局部修补的直接证据

最后一格原布局（80株全田方案）：

```text
土豆  土豆  土豆
土豆  空    番茄
番茄  番茄  番茄
```

只修改三个坑后的布局（81株全田方案）：

```text
番茄  土豆  土豆
土豆  番茄  番茄
辣椒  番茄  番茄
```

本格从土豆4＋番茄4变为土豆3＋番茄5＋辣椒1。三维养分净变化仍为零，辣椒与相邻地皮的同族共同满足距离规则；其他地皮的作物数量、位置均不变。配比已不是两种各4，中心留空规则自然不再触发。

离线实验保持全部原始规则，固定邻域外的坑位，强制总量81，并最小化相对80株方案的改动坑数：

| 开放的邻域 | 最少改动坑数 | 状态 | 建模＋求解墙钟 |
|---|---:|---|---:|
| 仅缺口所在1格 | 3 | OPTIMAL | 0.079秒 |
| 右下2×2区域 | 3 | OPTIMAL | 0.150秒 |
| 整片9格 | 3 | OPTIMAL | 1.546秒 |

这是 CP-SAT 单线程的诊断实验。它证明存在小范围修补，以及这些实验中最少需改3坑；不能据此承诺 Lua 实现也只需0.079秒。
全田81达到容量上界，无需另做“排除82株”的复杂搜索即可证明数量最优。

来源：[完整布局与初始解](../evidence/cpsat-autumn-analysis-2026-11-16/witness.json)、[邻域实验](../evidence/cpsat-autumn-analysis-2026-11-16/neighborhoods.json)。

## 建议分三步实施，当前仅提出方案

### 优先级1：在初始解之后加入有界邻域修补

入口建议放在 `aom_seed_packing.Balanced` 的初始合法见证之后、`region_probe` 之前。

1. 如果已有合法解且距离安全上界较近，按“含空坑地皮 → 相邻两格 → 2×2等小连通邻域”逐步开放坑位。触发依据为缺口和工作量，不写季节、作物名、3×3田形特例。
2. 邻域外暂时固定，计算邻域可用的剩余库存，以及每个候选作物从固定外部获得的同族支持。
3. 复用现有合法单格配比，优先检查数量更高、与原布局改动更少的配比。允许换种类和用量；只交换已有作物不能覆盖本次解。
4. 既检查邻域内作物，也检查会受改动影响的邻域外作物。坑距冲突、养分和库存仍按全田规则处理。
5. 只接受全田完整校验通过的新方案。达到安全上界则证明数量最优并进入原排列阶段；只改善下界则更新已有解；预算用完或局部无解则继续原完整搜索。

固定外部仅是一次候选搜索的条件，不是全局约束。任何局部失败、超时或配比截断都不能降低全田上界或宣称全局无解。

借鉴的是 CP-SAT 的“已有解引导＋大邻域搜索/修复”思想，不是把 CP-SAT 引入 Mod。OR-Tools 9.14 的官方参数明确提供 LNS、解池和 hint repair；原先无提示的 CP-SAT 对照并未记录哪个内部子求解器产生最终解，不能断言其胜因必然是 LNS。[官方参数定义](https://raw.githubusercontent.com/google/or-tools/v9.14/ortools/sat/sat_parameters.proto)

### 优先级2：让不限全局配额的搜索提前并持续推进

- 不把完整/大批量配额枚举作为所有路径的前置条件；先允许以库存上限、总数目标、逐地皮配比和同族约束直接搜索。
- 配额逐批生成，只作为候选顺序、可证明的界或额外传播信息。部分配额不覆盖所有解时，不能约束完整路径。
- 将现有合法布局真正用作优先赋值的起点，优先保留不冲突的坑位，而不是主要由配额顺序重新组织整个布局。
- 用每条方法实际工作量/CPU消耗和是否改善上下界调整份额；主完整路径必须持续推进。辅助方法进入第二条精确搜索后，不应自动继承8倍恢复次数。

这一步改动面比邻域修补大，建议在第一步独立验证后再进行，避免同时改变多个变量而难以判断收益来源。

### 优先级3：加强边界支持与单格配比之间的传播

当前已有同族支持传播和配比上下界，并非完全没有剪枝。可以补充“某个具体配比能否给必种边界坑提供同族支持”的检查：

对坑位、候选作物和单格配比，计算本格可用同族数量加外部可用同族支持的安全上界。若小于最低同族数，则该组合不可能；如果一个必种坑在该配比下已没有任何可选作物，则可排除该配比。

对本次角坑，这能更早识别每类最多3株的配比不适用。必须使用实际邻接关系，而不是硬编码“角落至少4株”；其他坐标、田形和坑位可能有不同外部支持。

本轮不优先引入通用冲突学习、完整 SAT 内核或大规模传播器重写。先解决已有合法解复用、搜索入口和调度这几个已经有证据的问题。

## 验证与验收建议

- 先分别验证邻域修补、搜索调度、传播增强的收益，再评估组合版本。
- 原48场景全部重跑，并扩展到已有完整审计场景、异形田、不同季节及库存、63/64格大田。不得依赖特定作物名或某张田形。
- 增加平移/旋转、负坐标、半径临界浮点距离、边界支持来自邻域外、改动导致邻域外作物失去同族、库存刚好用尽、局部无解而全局有解等回归。
- 与独立校验及 CP-SAT 已证明的结果对照，最大合法株数不能下降；空结果、超时和未证明必须如实区分。
- 单独记录首次合法解、首次达到上界、数量证明、排列、总墙钟、CPU与搜索节点。多轮固定快照测速，避开或明确记录其他 CPU 密集任务。
- 建议性能目标：本场景达到81株的数量阶段稳定降到1秒量级；这是待验证目标，不是已实现成绩。对原本很快的场景，检查新增探测的绝对开销和P95/P99，避免平均提速掩盖尾部退化。
- 离线性能通过后，游戏内主线程卡顿和联机体验仍需单独验收。

若后续进入实现，建议从优先级1的小范围原型开始。本次只完成诊断和方案，尚未对任何 Mod 文件实施这些优化。
