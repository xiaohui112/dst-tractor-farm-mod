# 巨大化播种等待优化备选方案

状态：**主要路径已在0.5.17实现，其余保留为备选**。原记录日期：2026-11-15；原分析基线：0.5.13。

0.5.17已实现输入快照校验、同田完整方案缓存、有效任务暂停接续、目标田明确后的低额度预计算、世界共享分帧预算、搜索方法交替推进和大田连续区域构造。预计算采用骑乘空闲且没有正式计划时、间隔2秒的两次稳定采样；尚未实现无目标田时仅因挂载设备就提前枚举组合，也没有扩大64格上限。实测结果和限制见[0.5.17验证报告](../evidence/0.5.17-planner-optimization-report.md)。

以下保留最初讨论与当时测量，未逐项改写为当前行为。现行行为以[播种机说明](../equipment/03-播种机.md)及运行代码为准。

## 目标与边界

目标是减少玩家从请求巨大化播种到实际播下第一颗种子的等待，尽量利用装料、整理背包和驾驶途中已有的时间。

保留当前规则：在应季、库存、坑距与密度、逐株同族、逐地皮养分净变化为零及双种4＋4中心留空的约束内，证明整片目标农田的最大合法播种量，再整理同族紧凑和排列。这里的“最大”只针对本轮选定的完整有效连通区域，不包含尚未开垦、以后扩建或其它独立农田；布局合法也不代替原版生长过程中的水分、照料等条件。

提前计算不自动开启作业，不扣种子、燃料或耐久，不占用货仓物料，不提前锁定正式播种计划。顺序播种仍按原有规则执行。正式开始播种后，继续遵守既有坐标锁定、现场复核、成功后结算及旧计划续播规则。

## 当前等待来自哪里

当前从实际作业入口触发规划，主要经过三个步骤：

1. 从当前地皮扫描四边连通、具备完整空九宫格的有效农田，最多64格；不是扫描整个世界。缺坑或被占用地皮不能作为桥梁。
2. 根据完整区域、季节和库存，寻找合法布局，并证明不存在播种数量更多的合法布局。
3. 数量固定后，运行一次有候选预算的紧凑与整齐优化；完成并复核后才能播种。

主要瓶颈是第二步的组合与空间搜索。扫描范围越大，参与搜索的坑位越多，但减少地图扫描本身不等于消除求解时间。五格以内也可能出现复杂实例。

规划在服务端Lua协程中分帧执行：每次恢复后检查约4毫秒CPU额度，每帧最多恢复128次；未完成则约下一游戏帧继续。4毫秒是协作式软额度，不是强制抢占上限。计算时间会被分散到多帧，离线CPU耗时不能直接当作玩家等待时间。

### 已有证据与本次观察

[0.5.13分阶段验证报告](../evidence/0.5.13-seed-optimization-report.md)记录了1162个完成场景，其中711个有播种结果：数量阶段CPU耗时中位数约0.2335秒、P95约2.6939秒、最大约13.7397秒；排列阶段中位数约0.0566秒、P95约0.2837秒。报告数据属于既有离线验证。

本次讨论另以当前Lua5.1源码、原版定义和测试地图桩做了单次队列模拟，加入函数计时，使用原始`Start`调度，并在完成回调处阻止实际播种以隔离规划成本：

| 场景 | 最大株数 | 数量CPU秒 | 排列CPU秒 | 调度次数 | 按30次/秒折算等待 |
|---|---:|---:|---:|---:|---:|
| 秋季两格横田，胡萝卜/玉米/土豆各6颗 | 18 | 约0.021 | 约0.010 | 7 | 约0.23秒 |
| `spring/plus-5/all-six`，春季五格十字田、全部当季作物各6颗 | 45 | 约10.516 | 约0.183 | 1575 | 约52.5秒 |

第二例使用15格测试货仓；其数量阶段包含约3.94秒的分块见证试探，后续仍需继续求解。该计时与内部精确求解计时有嵌套，不能相加统计。

这些是本次诊断的单次近似观察，未作为新的发布验收，未保存完整基准产物；计时插桩及机器负载会影响结果。折算等待不是实际客户端测量，也不能据截图确定玩家当时的库存和完整区域。后续实施前应重新建立可复现基准。

## 首选方向：分阶段提前计算

建议组合：**装上播种机后准备组合 → 库存稳定且目标农田明确后完整预计算 → 请求巨大化播种时复核并使用结果，或接续未完成任务。**

| 触发时机 | 建议动作 | 优先级与限制 |
|---|---|---|
| 装上播种机，已有可识别种子 | 准备季节、库存相关的互补组合和候选库 | 不要求当前是巨大化策略；没有目标农田时只做与几何无关的准备 |
| 连续装料结束、库存稳定 | 更新库存快照，合并变化后再计算 | 可评估最后一次变化后0.5～1秒再启动；数值只是候选，尚未验证 |
| 靠近或进入可播农田，目标区域明确 | 扫描完整有效连通区域，启动完整数量求解及排列整理 | 同一时刻优先处理最可能使用的一片田，避免沿路遍历所有农田 |
| 在同一片田内移动 | 更新当前执行位置，继续已有任务 | 不因当前地皮改变而重启整片规划；不同起点扫描顺序应归一化 |
| 切换到巨大化 | 提高同一任务的调度优先级 | 不因切换动作丢掉有效的预计算结果 |
| 按F开始巨大化播种 | 复核并提交有效的已证明方案；未完成则接续搜索 | 只有完成证明与既有排列阶段后才交付，不把中间候选直接播下 |
| 暂停作业、暂时切回顺序策略 | 保留仍有效的任务或结果，可暂停重计算 | 顺序实际播种会改变现场和库存，届时需使旧预计算失效 |
| 收获、清理并恢复同样九宫格后再播 | 尝试上一轮完整方案缓存 | 必须重新确认适用条件；只因田形相同不能直接复用最优结论 |

仅装上播种机，不足以确定完整空间问题。可能还没装种子、离农田很远，或者玩家将去另一片田。附近有多片候选农田时，目标选择的距离、切换滞后及缓存数量留待后续测量确定；预计算目标必须在实际请求时重新确认。

## 有效性、取消与复用

预计算任务与正式执行计划分开保存。当前`Start`依赖`_working`且要求巨大化策略，停工或切换策略会清理任务，不能简单把现有`Start`移到挂载回调。建议未来建立独立的预计算生命周期，切策略时只改变优先级；已有正式计划和旧版计划的续播保持原语义。

### 输入标识与失效条件

预计算记录应能够对应：服务端世界、完整目标区域及实际坑位、季节、各作物有效种子数量、参与求解的作物定义和约束版本。地皮顺序及货仓槽位顺序应规范化，避免同一问题因起点或换槽位重复计算。

| 变化 | 处理原则 |
|---|---|
| 仅换货仓槽位，各作物数量未变 | 保留 |
| 同一完整区域内移动，现场未变 | 保留；当前要播哪格另行决定 |
| 增减有效种子、堆叠数量变化 | 重新确认输入；旧布局可作为候选，但旧最优证明不能自动沿用 |
| 放入无关物品或不参与本轮求解的种子 | 以规范化后的有效输入是否变化判断，不因所有货仓事件一律重算 |
| 缺坑、作物/障碍变化、连通桥梁消失、增添相连地皮 | 使受影响区域的完整结果失效，必要时重新扫描 |
| 季节变化、作物定义或约束变化 | 重新准备并求解 |
| 暂停或切策略，输入未变 | 可以保留；暂停本身不是问题输入变化 |
| 卸载设备、车体销毁或世界卸载 | 停止任务和回调并释放资源；有界纯数据缓存是否保留另行评估 |

库存事件需要同时覆盖物品移入移出与堆叠数量变化，不能只依赖`itemget`/`itemlose`。应合并连续变化，避免装料期间反复启动。采用任务代次或等效机制，防止已经作废的旧回调覆盖新任务。

实际提交前重新读取季节、库存和完整区域现场，确认与求解快照一致；版本标记只能帮助快速排除，不能替代关键现场复核。任意输入变化后，旧方案“仍然合法”不等于“仍然最多”：种子增加或区域扩大可能出现更优方案；种子减少也不能截掉旧布局的一部分后宣称最优。

### 缓存层次

1. 已有互补组合与候选库缓存：继续利用；先确认现有命中情况，避免重复建设。
2. 完整已证明方案：用于相同输入的下一轮，命中后现场复核再使用。
3. 未完成搜索：同一输入下保留协程或等效恢复状态，避免暂停后从零计算；不要求跨存档持久化Lua协程。
4. 输入变化后的旧布局：只作合法候选或求解起点，重新验证并建立当前问题的数量证明。

缓存应有数量、内存和闲置时长上限。超时或预算截断的分支不能缓存为无解。当前部分模块持有共享回调、阶段统计和搜索上下文；多任务轮转前需隔离或明确串行化这些状态，避免任务互相覆盖。

## 调度和提示如何减少等待感

后台预计算仍占用游戏主线程时间，并不增加总算力。建议服务端按世界统一管理计算额度，多辆拖拉机共享预算，避免每台各用一份预算导致累积卡顿。

玩家尚未请求巨大化时低优先级计算；请求后接续同一任务并适当提高优先级。具体额度需测实际帧耗时再定，不能把现有4毫秒简单调大就宣称解决问题；长循环的让出点也需要评估。

准备期间尽量安静，不反复头顶喊话，不阻止驾驶、装料或顺序作业。已有仪表提示如需增加，应保持简短。只有玩家请求巨大化而结果未完成时，再显示真实阶段，例如“正在计算最大播种量”“正在整理排列”；没有可靠估计时不显示百分比或剩余秒数。

状态文案只能报告确实完成的阶段。后台计算不能自行开启F、自动消耗材料，或者在玩家已经离开目标区域后提交过期结果。

## 其它备选路径与取舍

| 路径 | 作用 | 最大合法数量保证及限制 |
|---|---|---|
| 减少重复试探、复用搜索状态、改进分支顺序与安全剪枝 | 降低实际CPU成本，重点关注复杂数量阶段 | 可保留；必须通过对照与独立校验，不能把未找到当成无解 |
| 快速构造布局并核对全田安全上界 | 容易实例一旦达到上界即可结束数量搜索 | 合法见证达到适用的安全上界，即可证明最大；未达到则继续完整求解。当前已有此机制，后续是提升覆盖率 |
| 当前格＋周围八格随车滚动求解并立即播种 | 缩小单次问题，可能更快播下第一颗 | 通常只能保证局部结果；库存全田共享、同族跨格且已播位置固定，会损失全田最大数量，不作为等价替代 |
| 用九格或其它局部窗口构造候选，再合并并全田验证 | 为全局求解提供可行起点 | 可保留；只有全田方案合法且最大数量已证明后才正式执行 |
| 先求全田最大数量，再任由局部窗口填坑 | 尝试提前执行 | 仅知道数量不够，局部决定未必能扩展为完整最大方案；不能据此保证最多 |
| 减少排列整理预算或只重算受影响的评分 | 降低整理开销 | 不改变已证明数量，但可能影响紧凑或整齐程度；复杂样例中收益较小，优先级较后 |
| 限时搜索，到时使用当前合法方案 | 控制最长等待 | 未达到安全上界或完成证明时，不能保证最多；属于玩法取舍，本方案不采用 |

如希望未完成全田布局就提前播种，必须先证明这些落子仍能扩展成全田最大合法方案；该证明本身可能仍需全局搜索，不能默认免费获得。

## 后续需要优化时的建议顺序

1. 建立基准：同时记录扫描、数量、排列CPU耗时，玩家请求到第一颗实际落种的墙钟时间，以及每次规划切片的帧成本。
2. 先做输入规范化、连续库存变化合并、同田移动复用和有效任务暂停恢复，减少重复工作。
3. 再加入挂载时准备、目标田明确后的完整预计算、请求时接续与复核；顺序策略允许低优先级准备。
4. 增加有界完整方案缓存，重点验证跨轮复用和现场变化失效。
5. 对剩余复杂长尾优化搜索路径，最后结合实机测量调整调度额度及排列成本。

以上只是重新启动优化时的参考顺序，当前不创建实施任务，不承诺启动时间或提速倍数。提前量不足、刚装好立即播或临时更换大量种子的场景，仍可能等待。

## 未来验收依据

- 正确性：相同输入的最大合法数量不低于当前完整求解结果，布局独立校验通过；未证明的结果不标记为最优，不用截断状态证明无解。
- 复用：同田移动、暂停恢复、槽位重排不重复启动；连续装料被合并；库存增减、堆叠变化、季节切换及地形/坑位变化能够作废旧结果。
- 执行：按F之前无播种及农业成本；后台结果不覆盖正式进行中的计划；旧计划续播、缺料停工和存档兼容保持现行规则。
- 体验：分别测有提前准备和立即作业两组，记录请求到第一颗落种的中位数、P95与最长等待；另记录后台总CPU及缓存命中，避免只把成本藏到别处。
- 实机：测单机、联机服务端和多车并存下的平均及长尾帧耗时、任务取消与资源清理。离线队列模拟不能替代这些结果。

数值目标等未来取得实机基线后再定。本轮没有实施或验证上述新增机制。
