# 播种机：设计、操作与实现

当前源码：0.5.18 后续静态目录重构，提供“巨大化·模版”和“巨大化·最优”两种规划。两者都满足逐地皮互补和原版位置条件；最优策略保留最大合法播种量证明。不读取地皮当前肥力。

等待优化的原始讨论见[备选方案](../proposals/巨大化播种等待优化备选方案.md)；0.5.17已实施部分以本文及版本报告为准。

## 参数与操作

| 项目 | 实现 |
|---|---|
| prefab / 类型 | aom_seeder / seeder |
| 配方 | 木板6、绳子4、普通种子20、齿轮1；园艺栏，炼金引擎 |
| 耐久 / 修理 | 100；拿起燧石左键挂件图标，或右键地面设备，每份+10 |
| 物料 | 15格货仓内的种子；巨大化仅使用能识别具体作物的种子 |
| 成本 | 成功种植一颗扣种子1、燃料1、底盘和挂件耐久各1；行驶燃料另计 |

空手左键表盘按“顺序→巨大化·模版→巨大化·最优→顺序”切换；切换停工并清除本轮计划，再按F开始。右键卸载，手持物品优先维修或装料。规划完成显示待播坑位的绿色预览（模版策略按玩家附近窗口显示，跨地皮移动刷新；最优策略显示整片）并提示“规划完成，开始播种”，两秒后自动播种，无需手工确认；已播标记移除，下车或切策略清除预览。顺序策略取货仓第一个有效种子，只种当前地皮空坑。

## 巨大化·模版

静态[角色格子目录](../template-catalog/README.md)逐图登记四季截图36项，其中28项九宫格启用，7项六角/错位和1项含非巨大化作物示例禁用。另有独立编号的两项18株程序方案（6＋12与6＋6＋6），不标成截图转录。单格4＋4留中心坑；双格16株保留两处指定空坑；四格32株保留四角空坑。同配比的双格重复与四格图案分别存在，原图重复条目也不合并。

作物替换仅取每条原图明确的OR，一个角色整块选一种作物；不按养分相同自由替换。季节由实际作物和原版定义求交集。构建脚本自动生成株数、库存、每地皮组成、角色坑位及去重的旋转/镜像；运行时直接require Lua数据。原图四地皮番茄＋土豆/茄子32株按四角留空复现，模版策略不套用最优策略通用单格4＋4中心空坑的形状限制，仍严格检查净养分与真实距离。

按季节、库存、真实坑位筛选模版，在完整可放置的地皮块上有限选配和拆换回填；选配最多48轮构造与64轮整块替换；候选比较额度为120000与一次完整候选遍历量的较大者，防止大田后半段被旧固定额度截掉。保留模版内部坑位、配比与空坑，不做逐坑调整。全田候选先比株数，再比留空集中、整体整齐与固定编号/方向/位置；不固定小块优先。不能放下合法模版的边角可以留空；不规则农田可能比最优策略少播，不把该结果宣称为全田最大。这里不采用货仓先后顺序优先规则。

两种巨大化策略共用实际坑距、同族、应季、库存与逐格养分互补校验。模版选配入口与最优入口独立。最优的`aom_seed_initial.lua`保留通用几何构造，额外读取`aom_seed_template_data.lua`的静态候选，只采纳株数更多且通过最优规则的完整见证，不调用模版选配入口；目录改变仍可能影响最优下界与耗时，必须回归。结果和计时放在设备本轮`_aom_planning_task`，模版不写最优模块的`last_report`。模版方案、最优方案的缓存键与存档策略隔离，并纳入目录版本和锁定编号；旧存档的GIANT继续对应“巨大化·最优”。切换仍停止作业并清除旧预览。

## 巨大化·最优原则优先级

1. **硬约束**：应季、库存足够、实际坑距和密度合格、逐株同族合格；每块地皮按原版消耗与回补定义计算，三类养分净变化均为零，禁止跨地皮抵消。通用双种4＋4图案保留中心空坑。
2. **播种数量**：在上述条件内求出并证明最大合法播种量；未完成证明不交付较少株数的计划。必要空坑不拿来补一株，库存充足也不会把4＋4改成5＋4。
3. **同族紧凑**：先比较同族分散分量，再比较最近三个同族的距离和。
4. **排列整齐**：前面指标相同后，比较行列、相邻地皮连续与重复图案。

种类更多、占地更少不再是压过紧凑或整齐的独立优先级。加权 `score` 仅保留作诊断；实际排列采用 `fragmentation → family → tidy` 的严格顺序。

“不读取当前土壤肥力”与“作物配比互补”是独立规则。贫瘠不会阻拦播种，也不提示缺肥；水分、施肥、照料、杂草和后续生长仍由原版与对应挂件处理。互补不保证任何初始环境下都无养分压力，也不代替实际生长验收。

## 扫描、规划与执行

按F从当前地皮扫描四边连通的完整空九宫格，复核真实土坑、作物和障碍。索引只作缓存，重启后也按现场恢复。缺坑或被占用的地皮不能作为桥梁。模版策略不设固定地皮总数上限，处理完整连通范围；最优策略最多64块，超限拒绝，不截取一部分后宣称整片最优。

`aom_seed_balance.lua` 从原版 `PLANT_DEFS` 推导每株净变化，完整枚举单格至多九株的互补数量组合，并求库存分配和安全数量上界。没有作物名称、季节配方或地形专用分支。随机种子、反季种子及不足同族最低数量的种子留在仓内。

`aom_seed_packing.lua` 分成两个阶段：先求最大合法播种量，再仅对这个数量运行一次紧凑/整齐优化。中间候选不会消耗排列整理预算。数量阶段先计算连续上界与完整枚举得到的整数上界；`aom_seed_feasible.lua` 和 `aom_seed_heuristic.lua` 只寻找可行见证、提供下界，其中的截断不构成不可行或最优证明。后备构造采用差量同族检查及有界几何候选缓存。

`aom_seed_exact.lua` 对坑位域、逐格互补组合、库存、坑距与逐株同族进行完整约束搜索，包含容量匹配、四至七株完整同族组覆盖、空闲区域连通性及数量传播。数量小于安全上界时必须完整排除更大的目标，才能返回当前数量；达到安全上界的合法见证本身即为最大数量证明。不使用作物名称、库存案例、预制地形答案或开发用整数规划结果来决定布局。

固定目标数量后，库存分配联立总株数与两维净变化，直接解出最多三个作物数量；相同向量、同族条件的库存按可整体改名的规范代表枚举。互补单格数量组合采用有界缓存。数量阶段可以将目标库存动态拆成互补子组，分别在真实小块地皮上构造、校验并合并见证，也可以探测紧凑地皮子集。分组或子集失败均不排除原问题，不降低目标。完整后备搜索轮流恢复各配额的搜索栈，并缓存已经完整排除的状态；任一完整搜索证明某配额无解后，停止该配额的其它分支顺序。预算截断状态不会当成无解缓存。

数量目标固定后，候选配比优先尝试同族在单格内支持较多的组成，仅改变分支顺序。候选最终仍按实际坐标、原版同族与逐地皮净变化复核。没有按作物名称、特定库存或田形设置解答。

求解在服务端Lua协程中分帧运行。候选探测采用确定的工作量预算，最终数量证明没有“超预算就交付少播方案”的后门；复杂实例可能耗时较长，可停止作业取消。`optimal=true` 只用于已经证明的最大数量。紧凑与整齐阶段仍采用有限候选预算，实际比较顺序为 `fragmentation → family → tidy`，不宣称其全局最优。完成后再次校验季节、库存、坑距、同族与逐格配比。

游戏分帧调度每次恢复后检查约4毫秒的CPU软额度，每次最多恢复1024次协程；同一游戏帧的预算由世界内规划任务共享。后台预计算额度为1毫秒。到额度只把同一搜索栈推迟到下一帧，不结束搜索、不改变数量目标或方案优先级。离线网页直接调用相同的 `Build` 与原始求解模块，执行调度不同，求解规则一致。

每次新计划记录 `quantity_seconds` 和 `arrangement_seconds`，分别表示最大数量求解与固定数量排列整理的进程CPU耗时；离线报告同时记录端到端墙钟耗时。CPU统计不作为搜索截止条件。游戏协程等待和渲染不等同于离线CPU时间。

0.5.18先用有限模版构造提供合法下界；连续区域未达到上界时，已验证的部分候选也保留。完整搜索复用不变候选域的上下界和同族域汇总，减少重复扫描。所有新构造都只提供下界，失败不排除任何合法解，未完成数量证明不交付少播结果。复杂实例仍可能很慢，具体边界见[0.5.18回归报告](../evidence/0.5.18-strategy-report.md)。

0.5.17数量阶段交替推进持续完整搜索与构造路径，保留完整搜索栈；更好的合法下界可更新分支提示，构造失败不排除全田解。大田先探测连续区域、多配比组合，并在必要时调用原始精确算法安排局部真实坑位；达到全田安全上界且整片验证通过才接受。其它场景继续完整证明。

完整方案缓存最多8项，签名包含应季有效库存、实际坑位、季节、净变化向量、同族参数、坑距和密度。换槽位或同田换起点不失效，库存与现场变化会重新求解。停工可保留最多4项挂起任务，恢复时重新扫描并核对输入；清理计划、设备变化或输入变化取消旧任务。缓存不跨存档持久化。模版存档保存完整模块编号、世界原点、方向和角色选择，加载时逐坑重建比对；旧模版存档没有这些记录时丢弃计划并重新规划，旧GIANT最优存档仍兼容。

骑乘且空闲、挂载播种机、当前为空田时，每两秒核对目标与库存；连续两次一致才启动低额度预计算。提前计算不消耗种子、不自动开启作业、不提交播种计划；按F后可接管同一有效任务。开始正式播种前再次核对整片输入，变化则重新规划。后台任务不会主动扫描整个世界。

规划日志为 `tractor_giant_planning_master.log` / `tractor_giant_planning_caves.log`。开始记录版本与算法指纹，求解前写入库存和真实坑位；阶段切换和每两秒进展独立落盘，完成后汇总数量与排列CPU、切片分布及完整布局。原版 `GetTimeRealSeconds` 可用时记录毫秒来源的墙钟；CPU仍为执行区间的进程CPU，可能包含引擎其它线程。首种及整轮播种完成/中断另记，不逐搜索节点写日志。

开种后锁定整片计划。每次播种前复核现场与整套余种；不改种、不拔除、不拆坑。缺种、缺坑、冲突植物或季节变化保留进度并停工。成功后才扣料和记录，原版回调异常依据现场核对，避免重复种植和计费。收获、清理并重新准备九坑后开始新一轮。

## 保存与兼容

继续使用v4坐标存档与D4同步，新增 `nutrient_balanced=true` 标识新规则计划，并保存、读档校验该标识。旧v3/v4已开始计划保留原坐标续播，不把旧计划现场改种；完成后的新轮次统一使用新规则。服务器保存完整计划，客户端只显示进度及下一地皮待播坑，不参与求解。

## 网页与独立验证

本机网页位于 `web/giant-seed-verifier`，双击该目录的启动器打开。每次生成创建新的Lua 5.1环境，直接加载当前Mod原始模块；网页JavaScript只输入、绘图与导出。显示版本、源码哈希、与本机安装的模块是否一致，以及逐格养分净变化、同族和库存检查。

`tools/seed_strategy_audit.py` 用本机原版定义及独立Python多重集枚举/整数规划验证，不进入Mod运行代码。`structured`覆盖四季、库存阈值/尾数与16类地形；`holdout`生成固定种子随机连通地形；`symmetry`覆盖旋转/镜像。数量组合求解器放宽同族几何条件，作为安全上界；需要时再用逐坑空间整数规划寻找可行见证，超时明确保留未证明状态。

行为回归另覆盖真实播种入口、物料消耗、回调结算、异步取消、现场变化、存档与旧计划续播。离线回归不替代DST真实游戏、联机与生长验收。

0.5.11的1538场景旧报告保留作历史证据；其上界没有互补约束，不能作为本版巨大化配比正确的验收依据。

## 巨大化规划的消息与分阶段计时（0.5.17）

服务端流程是：开工记录点 → 作业/首次调度 → 扫描连通空九宫格 → 统计库存、筛选应季作物 → 逐地皮互补配比及最大数量证明 → 固定数量下整理排列 → 生成和复核真实坑位计划 → 提交计划、编码预览、设置网络变量 → 头顶“规划完成，开始播种” → 预览定时2秒 → 重新核验现场及库存 → 首颗种子种下。正在规划时仍只提示“正在规划巨大化布局，请稍候”，不会逐搜索分支反复喊话。

开始时写出`START/RULES/INPUT`，扫描后写出`PITS`，阶段切换写出`STAGE_BEGIN`，每两秒写出`PROGRESS`。规划完成后汇总写出`[Tractor][GiantPlan][车辆GUID-本运行期序号]`下的`INPUT`、`STEP`和`SUMMARY`。日志输出、2秒预览、开播复核及首颗种植的耗时属于完成后的步骤，会稍后用同一编号追加`STEP`和`FIRST_SEED`。实际没有执行的后备分支显示`status=skipped`及原因；失败或取消也会打印走到的阶段，当前未完成阶段不会冒充完成成绩。首种前停工追加`SOW_CANCELLED`，首种后中断追加`SOW_STOPPED`，全部播种完成追加`SOW_COMPLETE`。

主世界本机日志位置为`~/Documents/Klei/DoNotStarveTogether/tractor_giant_planning_master.log`；洞穴为同目录`tractor_giant_planning_caves.log`。这是服务端规划日志，加入别人服务器时应查看服务器所在机器的日志。搜索`[GiantPlan]`，按同一个任务编号查看整组记录。

### 时间与调度字段

所有`*_ms`字段均为毫秒。

| 字段 | 口径 |
|---|---|
| wall_ms | 引擎真实时间经过值，包含跨帧、暂停和调度延迟 |
| active_cpu_ms | 仅累计本任务执行片段内的进程CPU，排除片段间隔；仍可能包含并行引擎线程CPU，并包含计时插桩开销 |
| active_wall_ms | 本任务计时执行片段占用的真实时间 |
| wait_ms | `wall_ms - active_wall_ms`；片段之外的时间，包括帧间其他游戏工作、排队、暂停等，不等于进程没有消耗CPU |
| game_ms | 模拟时间差；配合真实时间观察暂停或游戏调度变慢 |
| process_cpu_span_ms | 整个区间内的进程CPU起止差，包含片段间游戏其他工作的CPU；用于对照旧计时口径，不能当作纯规划CPU |
| ticks / resumes | 调度次数/外层规划协程恢复次数；同一恢复可穿过多个阶段，细项计数不能直接相加 |
| cpu_budget_hits | 因约4毫秒软额度让出下一帧的次数 |
| resume_limit_hits | 因单次调度恢复达到1024次而让出下一帧的次数 |
| max_tick_cpu_ms | 单次规划调度的最大进程CPU，不含完成后的日志输出 |
| max_resume_cpu_ms / resumes_over_4ms | 最长单次恢复及超4毫秒的恢复次数；协作式调度无法抢占未yield的长恢复 |
| max_dispatch_gap_ms | 两次规划调度之间最大的真实时间间隔 |
| request_to_seed_wall_ms | 服务端开工记录点（自动新轮次为入口）至第一颗实际播下的真实时间；不包含客户端按键上行网络时间 |
| plan_to_seed_wall_ms | 规划提交完成至首种，包含日志输出、预览、复核和必要的行驶等待 |
| request_to_seed_active_cpu_ms | 同一段流程中累计的执行片段CPU，包括完成日志和首种步骤 |

真实时间使用原版`GetTimeRealSeconds()`，其来源为引擎毫秒时钟。缺少此API时回退到`os.time()`，明确标为`wall_clock=system_wall_seconds`及`wall_precision_ms=1000`，不冒充毫秒精度。后台任务按F接管后，首种等待从本次F请求计起，规划总时间仍保留提前计算的区间。

现有`os.clock()`起止差跨越协程暂停时，会把游戏在间隔中消耗的进程CPU也计入阶段。0.5.16游戏入口改用执行片段累计值记录两阶段耗时；网页同步入口仍使用连续运行的`process_cpu`口径。先用相同版本、季节、田形、库存，对照数量/排列CPU，再比较游戏的等待与调度字段。`INPUT`保留实际季节、库存、地皮中心、数量证明模式/节点数及排列试次数，便于复现。

例如每秒约30次调度、每次约4毫秒CPU软额度，理论可分配给此任务的进程CPU约为每秒0.12秒；离线1秒CPU不等于游戏只等1秒。实际还受1024次恢复上限、单次长恢复、引擎其他工作与2秒预览影响，具体以日志为准。多线程进程CPU也不能直接当作单个Lua线程的CPU或GPU时间。当前没有测量客户端网络接收延迟、GPU出帧时间或独立GC耗时，也不依据这些计时估算剩余秒数。

## 0.5.19模版大田执行与预览

模版扫描、最终校验和全田评分通过协程分帧推进；模版开工不在创建任务前同步扫描整田，也不再通过空闲预计算重复扫描大田。暂停可以接续原协程，提交前在协程内复核完整输入；输入变化时重新规划。最优策略的证明分支、数量目标、分帧预算与64块上限保留。

服务器保留全田坑位、完整模块和逐株进度，存档不受64块或576株限制。每次开播只复核当前完整模块的全部地皮和坑位，整田剩余库存由成功播种／现场识别完成事件更新；远处模块会在到达该模块时复核。缺坑、作物丢失、库存不足仍停止播种。

D6预览按静态模版编号、方向、角色作物、模块原点和待播位掩码编码；实际坑位偏移单独保留四位小数。只发送骑手地皮中心沿两轴各±20世界单位内的附近模块，单包最多64个模块、512株待播点、24000字符。移动跨地皮或播种完成后刷新；客户端移除旧窗口标记。这个窗口限制只作用于预览，不截断全田计划或存档。D5／D4旧协议继续严格按原限制解析，最优策略仍用D5。

取消地皮上限不代表任意大农田都能立即完成。扫描、静态候选准备和全田数据仍消耗CPU及内存，真实游戏等待还包含分帧与预览时间；实机FPS和联网表现需要重启后验收。

## 0.5.20双地皮18株配比覆盖

`program-18-equal`固定三行六列角色格子，库存为6＋6＋6；`program-18-ratio`固定6＋12格子。这两项是已确认的程序扩展，构建目录时从原版作物定义中枚举共同应季、逐地皮养分净变化为零的不同作物组合，并逐格验证同族距离及坑距；运行时仅选配预生成数据，不做全田最大数量证明。相同需求只保留一个角色映射，优先保留原有映射。截图模版继续只允许原图OR替换，不能启用这项生成规则。

扩展配比会改变有界选配的候选顺序。扩展方案未达到库存／坑数上界时，另以原有候选和独立尝试额度构造完整方案，再按数量、紧凑和整齐比较两者。新增配比不会通过消耗原候选的尝试额度让旧方案丢失；代价是在部分混合库存下多执行一轮有界选配。最优策略继续证明最大合法数量后再优化排列，不因本次修复放宽目标。
