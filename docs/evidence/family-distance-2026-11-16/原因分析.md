# 同族半径边界浮点误判原因

2026-11-16。仅诊断，没有修改 Mod。

后续核对：已从本机原版 762172 macOS x64 引擎确认坐标及 FindEntities 距离采用 float32，等于半径边界会通过，未加 epsilon。这个具体例子的原版距离平方为 `15.999996185302734`。详见[原版边界核对](原版FindEntities边界核对.md)，其中区分了静态二进制证据、离线数值复现与尚未完成的游戏内查询实测。

## 已确认的原因

标准九宫格使用4/3坑距，坑坐标由“地皮中心＋偏移”生成。4/3无法用有限二进制浮点数精确表示，相同偏移与不同地皮中心相加时发生不同方向的舍入。

在 Lua 5.1 中实测：

```text
a = 8 + 4/3 = 9.3333333333333339
b = 4 + 4/3 = 5.333333333333333
a - b       = 4.0000000000000009
(a - b)^2   = 16.000000000000007
(a - b)^2 <= 16  → false
```

数学上 `(8+4/3)-(4+4/3)=4`，平方恰好为16。多出的 `7.105427357601002e-15` 来自浮点舍入，并非设计上真的把坑距设置成了超过4。

坐标生成见 `aom_farm_work.lua:GetMoundTargets`，离线输入构造见 `tools/cpsat_benchmark/benchmark.py:context`。规划器 `aom_seed_layout.lua:Geometry` 使用 `d<=radius^2` 建邻接表，首先漏掉这些边；后续 `Layout.Valid` 和其他求解路径又采用严格半径比较。只修改最后的校验是不够的，因为邻接表中的边已经缺失。

按标准九宫格整数索引计算该3×3场景的精确邻接关系，与现有双精度结果对照，共漏掉36条有向邻接边，即18对坑位；误差最大值就是上述约7.1e-15。

## 隔离反事实实验

冻结同一份旧源码，仅在离线进程中包装 `Layout.Geometry`：对超过半径平方不多于1e-10的边界值，恢复相应邻接并把该距离归一到半径平方。没有修改 Mod 文件、搜索顺序、库存、养分或初始构造策略。

结果：

- 原实现：前次10秒墙钟对照超时；另一次20秒CPU诊断仍停在80/81。
- 仅做上述几何数值处理：81株，上界81，`upper-bound-witness`。
- 数量阶段约0.154 CPU秒，进入整理的墙钟约0.174秒；两阶段合计约0.533秒。
- 无需进入全局配额准备或全局精确搜索。
- 输出通过标准九宫格整数索引的精确同族检查；原严格双精度校验仍会拒绝，进一步确认差异集中在几何边界模型。

该实验说明数值误判是此离线超时案例的重要直接触发因素。1e-10只是本次隔离诊断参数，不是已确定的生产修复阈值，也不是实机验收结果。

## 对前一轮结论的修正

应当把“数值边界及引擎一致性”提升为第一优先级，再决定是否需要局部修补或搜索调度优化。前一轮建议优先重排/修补，顺序过早。

此前把规划器的严格Lua比较直接称为“原版严格距离判定”也不够准确。本机原版 `farm_plants.lua:FamilyStressTest` 调用的是 `TheSim:FindEntities(..., family_check_dist, ...)`，实际边界由引擎实现处理。离线测试中的 Transform 只是直接保存 Lua 数值，并不模拟真实引擎的位置存储精度；不能把本次约1e-15的离线尾差直接断言为实机同族查询结果。

最终修复前应核对实际 Transform 坐标往返及 FindEntities 的临界邻居结果，统一坐标/几何判定、所有求解路径、最终校验和离线模型，再复跑测速。标准九宫格的精确索引可作为数学基准，但不能未经核实就覆盖现场真实偏移；也不应仅四舍五入显示值来掩盖内部比较。
